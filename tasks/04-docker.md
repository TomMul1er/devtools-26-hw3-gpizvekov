# Часть 4. Упаковать сервис в Docker • 2 балла

На вашей машине всё работает, но у коллег может не быть нужного `Python`-окружения. Мы, к счастью для наших коллег, очень любим их! Поэтому в этой части вы создадите `Dockerfile` и `.dockerignore`, упакуете сервис в образ и выясните, что видит контейнер.

Образ собирается из корня проекта:

```bash
docker build -t csv-reports:1 .
```

## 4.1. Образ и HTTP • 1 балл

**Требования:**

- Команда `python3` в контейнере запускает Python 3.12 или новее.
- В образ входят зависимости из `requirements.txt`, код и HTML-шаблоны приложения.
- Параметры `HOST`, `PORT` и `DATA_DIR` образ принимает через окружение. По умолчанию сервер слушает порт `8080` на сетевом интерфейсе контейнера и хранит данные в `/data`.
- Диагностические сообщения приложения идут в stdout и stderr, чтобы их было видно через `docker logs`.

## 4.2. Пользователь, контекст сборки и кэш • 1 балл

**Требования:**

- Процесс работает от непривилегированного пользователя с UID `10001` и GID `10001`.
- Данные хранятся в `/data`. Каталог создаётся в образе, его владелец `10001:10001`. Приложение может писать в пустой том Docker, смонтированный в `/data`.
- Инструкцию `VOLUME` в Dockerfile не используйте. Сначала вы изучите хранение внутри контейнера, а в части 5 подключите хранилище явно при запуске.
- В контекст сборки не попадают `.git`, `.venv`, `.env`, рабочие данные, логи и резервные копии. Реальные секреты для проверки этого требования не добавляйте.
- Если кэш доступен, правка только Python-кода не заставляет заново устанавливать зависимости.

Проверьте, от какого пользователя запускается контейнер:

```bash
docker run --rm --entrypoint python3 csv-reports:1 -c 'import os; print(os.getuid(), os.getgid())'
```

Ожидаемый вывод – `10001 10001`.

## 4.3. Откуда доступен сервис?

1. Убедитесь, что порт хоста `18080` свободен.
2. Запустите контейнер без публикации порта. Проверьте `/health` **изнутри контейнера** любым способом, доступным в образе.
3. С хоста обратитесь к `http://127.0.0.1:18080/health`. Сравните с запросом изнутри контейнера.
4. Пересоздайте контейнер с публикацией порта хоста `18080` в порт контейнера `8080`. Проверьте с хоста:
   ```bash
   curl -i http://127.0.0.1:18080/health
   bash scripts/submit.sh http://127.0.0.1:18080 samples/clean.csv work/from-container.json
   ```

   Убедитесь, что `/health` вернул HTTP 200. В `work/from-container.json` должны быть имя `clean.csv` и ID созданного отчёта.
5. Остановите и удалите этот контейнер, чтобы освободить порт. Создайте новый с той же публикацией, но задайте серверу `HOST=127.0.0.1`. Сравните доступ изнутри и снаружи.
6. Пересоздайте контейнер с рабочими настройками.

> **На подумать.** Где находится `localhost` в каждом из запросов? Почему одного `EXPOSE` недостаточно, чтобы достучаться до сервиса через порт хоста?

## 4.4. Что видит каждый из двух контейнеров?

Оставьте первый контейнер запущенным без тома. Запустите второй из того же образа без публикации порта.

1. Создайте файл `/data/only-first` в первом контейнере. Проверьте, виден ли он во втором.
2. Сравните версии ядра Linux в обоих контейнерах.

> **На подумать.** Что у этих контейнеров общее, а какие данные есть только у первого?

**По желанию · Почему у одного процесса два PID?** Найдите основной процесс первого контейнера в `docker top`. Сверьте его PID с полем `State.Pid` из `docker inspect`, а команду – с `/proc/1/cmdline` внутри контейнера. Почему внутри у процесса PID 1? На macOS PID из `docker top` относится к Linux-ВМ Docker.

Удалите второй контейнер. Первый понадобится в части 5.

## 4.5. Когда Docker заново устанавливает зависимости?

1. Добавьте комментарий в `Python`-код и пересоберите образ. По выводу сборки убедитесь, что шаг установки зависимостей взят из кэша.
2. В той же рабочей копии **добавьте комментарий** в `requirements.txt` и снова пересоберите образ. Сравните вывод с предыдущей сборкой. Время в секундах измерять не нужно.
3. Уберите оба комментария. Остальные изменения решения сохраните.

> **На подумать.** Какие шаги выполнились заново во второй сборке и почему?

Для части 5 оставьте один исправный контейнер без хранилища.

**По желанию · Почему контейнер завершился с кодом 137?**

Скрипт `tools/memory-demo.py` постепенно занимает 128 MiB. Дайте отдельному контейнеру 64 MiB. Если имя `reports-memory-test` занято, выберите свободное.

```bash
docker run -i --name reports-memory-test --memory 64m --memory-swap 64m \
  --entrypoint python3 csv-reports:1 - < tools/memory-demo.py
docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}' reports-memory-test
docker rm reports-memory-test
```

Какое из двух значений подтверждает, что контейнеру не хватило памяти?
