# Часть 3. Сделать надёжный HTTP-клиент • 1,5 балла

Сервер может ответить ошибкой, редиректом или оборвать передачу на середине. Мы же – фанаты стабильности! Клиент должен сохранять только полный успешный отчёт, а в остальных случаях сообщить об ошибке. В этой части вы допишете `scripts/submit.sh` и `scripts/probe.sh`, чтобы реализовать это.

## 3.1. Что можно узнать из HTTP-ответа?

Запустите сервер. Отправьте `samples/clean.csv` запросом `POST /reports` в поле формы `file`. [Пример запроса с curl](../interfaces.md#http).

Проверьте статус 201 и получите созданный отчёт по адресу из заголовка `Location`.

**По желанию · Как найти запрос в логе?** Возьмите `X-Request-ID` из заголовков ответа на POST. В терминале, где запущен сервер, найдите строку с тем же значением `request_id`.

**По желанию · Чем отличаются ошибки HTTP?** Сравните ответы на три запроса: `GET` по несуществующему пути, `DELETE /reports` и `POST /reports` с JSON вместо файла. Что нужно исправить в каждом запросе?

## 3.2. `submit.sh`: загрузка и обычные ошибки • 0,5 балла

Оставьте сервер запущенным. При первой загрузке `submit.sh` создаст файл отчёта `work/from-api.json` в рабочем каталоге из подготовки.

```bash
bash scripts/submit.sh http://127.0.0.1:8080 samples/clean.csv work/from-api.json
```

Сразу проверьте код завершения (`echo $?`) и откройте отчёт. Повторите команду с `samples/batch/broken.csv`, сохранив тот же выходной путь. Сравните код завершения и содержимое файла.

> **На подумать.** Скрипт сохранил JSON-ответ. Значит ли это, что он сохранил отчёт? Или нет?

Исправьте `scripts/submit.sh`. Аргументы по порядку: базовый URL, путь к `CSV` и путь к выходному `JSON`.

**Требования:**

- При HTTP 201 скрипт сохраняет тело ответа в выходной файл и возвращает `0`.
- При другом HTTP-статусе, сетевой ошибке или отсутствии входного файла скрипт возвращает ненулевой код и пишет причину в stderr.
- Если запрос неуспешен, выходной файл не создаётся и не перезаписывается.
- Если не удалось записать результат, скрипт возвращает ненулевой код, а старый выходной файл остаётся целым.
- HTTP 3xx считается ошибкой. По редиректу скрипт не переходит.
- Один запрос длится не больше 10 секунд. Повторять POST автоматически нельзя.

В проверках базовый URL имеет вид `http://127.0.0.1:PORT`, без пути и без `/` в конце. Каталог выходного файла уже существует, входной и выходной файлы различаются.

Повторите обе загрузки. Убедитесь, что после ошибки файл содержит первый отчёт.

## 3.3. `submit.sh`: обрыв передачи и сигналы • 0,5 балла

**Требования:**

- Статуса 201 недостаточно: передача тела ответа должна завершиться успешно. Обрезанный ответ считается ошибкой. Не оставляйте его копию рядом с выходным файлом.
- Временные файлы удаляются при успехе, при ошибке и при прерывании через `SIGINT` или `SIGTERM`.

### Почему отчёт обрезан, хотя статус 201?

Остановите обычный сервер. В его терминале запустите имитацию:

```bash
python tools/http-fixture.py --host 127.0.0.1 --port 8090
```

Отправьте `samples/clean.csv` через `submit.sh` на `http://127.0.0.1:8090` с прежним выходным путём `work/from-api.json`. Сервер отвечает 201, обещает в `Content-Length` больше байтов, чем передаёт, и обрывает соединение. Сравните код завершения и содержимое выходного файла с успешной загрузкой.

> **На подумать.** По каким признакам ответа можно заметить такой сбой?

### Что останется на диске после прерывания загрузки?

> `Ctrl+C` посылает сигнал прерывания (`SIGINT`) процессам переднего плана. Команда `kill -TERM <PID>` просит процесс с указанным PID завершиться (`SIGTERM`).

1. Перезапустите имитацию на том же адресе и порту с параметром `--upload-mode slow`. В этом режиме POST ждёт 15 секунд перед ответом.
2. Запустите `submit.sh` и нажмите `Ctrl+C`, пока он ждёт ответа.
3. Повторите загрузку. Из второго терминала выполните `kill -TERM <PID>`, подставив PID скрипта `submit.sh`.

После каждого запуска дождитесь завершения скрипта. Проверьте, что прежний выходной файл цел, а временные файлы удалены.

Скрипт может завершиться с задержкой. Почему Bash иногда ждёт дочерний процесс, объясняет [раздел о сигналах в руководстве Bash](https://www.gnu.org/software/bash/manual/html_node/Signals.html).

**Самопроверка.** Проверьте, что при обрыве передачи прежний отчёт остаётся цел:

```bash
python tools/self-check.py http
```

## 3.4. `probe.sh`: отвечает ли сервис • 0,5 балла

Допишите `scripts/probe.sh`:

```bash
bash scripts/probe.sh http://127.0.0.1:8090/ok
```

**Требования:**

- Скрипт выполняет GET по **полному URL** из аргумента.
- Код `0` скрипт возвращает только при HTTP 200 и успешно завершённой передаче.
- HTTP-ошибка, редирект, отказ соединения и таймаут дают ненулевой код.
- Скрипт ждёт ответа не дольше трёх секунд. Повторов и перехода по редиректам нет.

Оставьте имитацию запущенной на порту `8090`. Для проверки GET у неё есть четыре маршрута.

| Маршрут | Ответ |
|---|---|
| `/ok` | 200 |
| `/unavailable` | 503 |
| `/slow` | Ответ через 15 секунд |
| `/redirect` | 302 с `Location: /ok` |

1. Проверьте все четыре маршрута своим `probe.sh`.
2. Получите сам ответ `/redirect`, а затем конечный ответ после перехода по редиректу. Сравните их.
3. Запросите `/unavailable` обычным `curl` и посмотрите на HTTP-статус и `$?`. Повторите со своим `probe.sh`.
4. Остановите имитацию и повторите запрос. Сравните отказ соединения с ответом 503.

> **На подумать.** Почему проверка обычным `curl` могла считать недоступный сервис работающим?
